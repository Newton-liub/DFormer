## 给下级模型的执行指令

1. **当前任务与授权范围。** 继续执行 `perf/mmfr-a2-v3-pipeline-opt1`，scientific parent 保持 `MMFR-A2-train-integration-v3`，目标只是在当前实际云端环境中优化 corruption pipeline 的实现效率。当前 RTX 4090 有卡实例继续保持，因此本轮不要在各阶段之间停下来等待新的授权；按本指令顺序连续完成 CPU Opt-B、parity、条件式 GPU equivalence 和优化后 probe。本轮明确**未授权**：500 epoch、正式模型效果评价、5090 probe、official test、R1/S1/C1、修改模型结构、修改 reliability head、修改 loss、修改 A+MID-A、修改 corruption 数学、修改 selector/evaluator/main success gate。
2. **保留 Opt-A 为不可覆盖基线。** 当前实现提交 `5bc4e40` 作为 Opt-A checkpoint 保留。已确认的基线包括：128 cases / 1536 tensors / 0 mismatch；`_validate_batch_outputs_v3` 约 `0.509→0.0245 s`；clean-instrument 条件 helper `0.816→0.330 s/batch`；原 production-like 8-worker 条件约 `1.204→0.613 s/batch`。后续任何 Opt-B 修改都必须能够与此提交和原 v3 分开复现，不允许 squash 掉历史证据。
3. **由于当前机器只有 14 logical CPUs，Opt-B 先解决 CPU oversubscription，不准一上来开 10 个 corruption worker。** 第一轮固定 corruption parallel workers=`1`，固定 `cv2.setNumThreads(1)`，扫描 DataLoader workers=`0,2,4,8`。这是性能初筛，不修改 production config。每个条件使用相同真实 `train-dev`、相同 batch size 10、相同 seed、相同 corruption schedule。为了减少当前有卡实例空耗，第一轮允许使用 `5 warmup + 30 measured batches`；记录 helper mean/P50/P90/P95、DataLoader wait、CPU utilization、RSS、spec count。第一轮只负责淘汰明显差的配置。
4. **第一轮筛出的前两个 DataLoader 候选再做稳定复测。** 对排名最好的两个 DL-worker 设置，各运行 `10 warmup + 100 measured batches`。只有这两组需要稳定统计。与此同时记录 `torch.get_num_threads()`、`torch.get_num_interop_threads()`，但本轮暂时不要调用 `torch.set_num_threads()` 修改它们。
5. **验证 DataLoader worker 数是不是“纯性能参数”。** 这是硬门禁。针对 `workers=8` 和准备候选的 `workers=X`，固定相同 seed、epoch、iteration 和 sampler 状态，对至少 100 个连续 batch 比较训练 helper 之前的输入轨迹，至少包括 sample IDs/order、RGB tensor、Depth tensor、label tensor，以及 mirror/scale/crop/pad 后进入 MMFR helper 的 tensor SHA-256。只有当这些输入逐位一致时，才能把 worker 数变化视为 implementation-only execution change。若不一致，输出 `dataloader-worker-count-changes-training-input-trajectory=true`，则 production worker 数必须继续保持 `8`；不得为了速度采用新的 worker 数。
6. **随后进行 batch 内 ThreadPool 扫描。** 只在第一阶段选出的两个 CPU contention 最低环境中测试 persistent `ThreadPoolExecutor`。corruption worker 数只测 `1,2,4,6`，暂不测 8/10。不要每个 batch 创建/销毁线程池；线程池必须在训练运行期间持久存在。OpenCV 固定 `cv2.setNumThreads(1)`，避免 nested oversubscription。每个条件先 `5 warmup + 30 measured`，前两名再 `10 warmup + 100 measured`。
7. **ThreadPool 的 RNG 和 batch 顺序必须完全不变。** 每个 task 必须显式携带 `sample_slot`、`sample_id`、epoch、iteration、现有 seed words 和自身 sample 数据；每个 sample 继续独立构造冻结的 `PCG64(SeedSequence(words))`。禁止共享 RNG、按 thread completion order draw、使用 thread-local 新 seed 或 batch-level generator。worker 返回值必须包含 `sample_slot`，父线程最终严格按 `sample_slot=0..9` 恢复原 batch 顺序。线程调度可以变化，任何 scientific output 都不允许变化。
8. **禁止共享可写 buffer。** 不允许多个 ThreadPool worker 写入同一个 numpy array、torch tensor、metadata list 或 validity buffer。每个 worker 返回自己的独立结果，由父线程组装。可以共享只读 kernel/cache，但任何 cache 若存在 lazy mutation，必须预初始化或加以证明线程安全。
9. **本轮不要用 ProcessPool，也不要实现 CPU/GPU lookahead。** 如果 ThreadPool 无收益，可以明确输出 `Opt-B parallelization rejected`，保留 serial Opt-A；不要为了“必须并行”增加复杂度。如果 profiler 能证明 ThreadPool 因 GIL 而根本不能利用 CPU，可以在最终报告里提出 ProcessPool 方案，但不得自行生产化。本轮同样禁止 queue-depth=1 CPU/GPU overlap；那是下一轮候选，不属于当前授权。
10. **搜索过程可以使用小 parity subset，但最终候选必须重新跑完整 golden。** 运行参数搜索时，可使用固定 16/32-case subset 快速排错；确定最终 production candidate 后必须执行完整 `golden_a2_v3_corruption_parity.py verify`，要求：128 cases、1536 tensors、`mismatch_count=0`。除 tensor hash 外，sample_id、seed words、specs、severity、spec order、`V_state_final`、`depth_valid_post`、`R_syn`、`R_sup`、telemetry masks 和 metadata 都必须一致。
11. **最终候选必须做 3 次独立 deterministic repeat。** 相同输入和 seed 独立启动 3 次；三次的全部 128-case output hash、spec hash、metadata 必须完全一致。任何 thread scheduling nondeterminism 都判为 FAIL。不得自行设浮点容差掩盖差异；若出现浮点不一致，只报告 tensor 名称、affected elements、max/mean abs difference 和原因，停止 production adoption。
12. **Opt-B 的 production candidate 选择原则不是“线程最多”，而是实际 wall time 最小且 P95 稳定。** 如果例如 workers=1 与 workers=4 差距很小，优先选择简单、稳定、CPU 余量更大的实现。最终报告必须同时给 helper mean/P50/P95，而不是只给最好的一次。
13. **Opt-B CPU 收口后，自动获得一次短 GPU old-vs-new trajectory equivalence 授权，不需要再次停下来问。** 前提必须同时满足：完整 golden 0 mismatch、3 次 deterministic repeat PASS、scientific semantics unchanged。使用同一 4090、同一 pretrained、同一 seed、相同真实 `train-dev` batches、batch size 10、AMP+GradScaler。分别运行 old v3/Opt-A reference 与 optimized candidate，至少取得 `10 successful optimizer updates`。比较每次成功更新后的 batch/sample identity、corrupted Depth hash、target hash、seg loss、rel loss、GradScaler scale、step/skip、model shared parameters、reliability-head parameters、optimizer state。目标为逐位一致，`max_abs_difference=0`。如失败，本轮立即停止，禁止进入 optimized probe。
14. **若 DataLoader workers 最终从 8 改成其他数值，GPU equivalence 还必须验证训练输入轨迹一致；若 workers 改变导致输入轨迹不同，则不得采用该 worker 改动。** 可以保留 helper 内 ThreadPool 优化，但正式 DataLoader workers 恢复为冻结的 `8`，然后重新跑 GPU equivalence。
15. **GPU equivalence PASS 后，自动运行优化后的 RTX 4090 throughput probe。** 使用冻结 batch size 10、AMP、真实 train-dev。至少运行 `10 warmup + 60 successful measured updates`。同时报告两个口径：A）audit-compatible probe，保留旧 probe 所需证据和哈希；B）production-like throughput measurement，关闭每 step 将大 tensor 拷回 CPU 并 SHA-256 的非生产 telemetry，但仍保留必要的轻量统计。不要把两个数字混写。旧云端 audit probe 为 4.94 img/s，而之前 profiler 得到的 production-like 约 5.97 img/s，两者必须分别作为各自口径的 baseline，而不能交叉计算 speedup。旧 probe 本身已明确存在额外 telemetry/hash 开销。
16. **optimized GPU probe 必须输出这些核心指标：** overall step seconds、img/s、GPU utilization、GPU idle fraction、CPU utilization、DataLoader wait、corruption-helper wall time、H2D、forward/loss/backward/optimizer wall time、peak allocated/reserved VRAM、minimum free VRAM、AMP scale 和 skipped-step 数。目标是判断 CPU 优化后 GPU 是否真正被喂饱，而不是只看 helper benchmark。
17. **本轮暂不设人为的“必须达到 X img/s 才算成功”。** 只计算工程事实：`speedup_vs_original_audit_4090`、`speedup_vs_original_production_like_4090`，并重新估算 64,000 optimizer steps/500 epoch 的 pure-training wall time。不要因为结果没达到预想数字而继续修改科学代码。
18. **关于 checkpoint/resume，采用条件式复核。** 如果最终 production candidate 只改变 `_validate_batch_outputs_v3`/helper 内部纯函数优化，DataLoader workers 仍为 8，且没有增加持久跨 batch 状态，则旧 v3 checkpoint strict-reload gate 可以继续作为基础证据，不必重跑完整 parent-child-reference。若最终采用了以下任一改变：DataLoader worker 数变化、persistent ThreadPool 对跨 batch 生命周期有状态、训练 dispatch/iteration bookkeeping 改动，则必须在同一 4090 上重跑一次 checkpoint/resume equivalence。判定仍必须是 resumed child 与 uninterrupted reference 的 model、optimizer、GradScaler、RNG/component state 等价，而不是仅“能加载”。旧云端 gate 的标准见现有证据。
19. **不得为了显存或速度改 batch size。** 当前 4090 batch 10 虽然 validation 后最低 free VRAM 约 1.73 GiB，但没有 OOM。CPU pipeline 优化与显存决策分开；本轮不得把 batch 10 改成 8，也不得改分辨率或 validation protocol。
20. **本轮不测试 5090。** 只有优化后的 4090 throughput 和 500-epoch 成本重新算出来以后，才决定 5090 是否值得做配对 probe。禁止根据旧的 4.94 img/s 直接判断 5090，因为当前已经证明旧实现存在很大的 CPU 工程瓶颈。
21. **本轮仍禁止 500 epoch。** 即使 optimized 4090 probe 很漂亮，也只能把状态推进到 `pipeline-optimization-gpu-equivalence-and-probe-completed-awaiting-senior-review`。不得自动启动 one-arm corruption-v3 500e screening。正式 500e 仍需要用户单独授权。
22. **由于当前有卡实例持续计费，执行顺序要以减少空闲为原则。** 不要在每个小 benchmark 后耗时整理大段文档；先把 CPU search、parity、GPU equivalence 和 probe 连续做完，再统一更新文档和生成报告。如果遇到导致后续工作无法继续的 blocking bug，不要让 GPU 长时间空闲排查；立即停止当前任务并向用户报告，由用户决定是否切卡。当前 4090 的价格快照为 1.88 元/小时。
23. **最终 source identity 必须重新冻结。** 目前 `5bc4e40` 是 Opt-A 实现 checkpoint，不应直接作为正式长训练身份。最终 production candidate 通过全部 parity/GPU gate 后，再建立新的 clean commit，例如 `MMFR-A2-v3-pipeline-opt1-freeze` 对应 commit/tag；同时记录 scientific parent=`MMFR-A2-train-integration-v3`、`scientific_semantics_changed=false`、生产代码 SHA-256 和 qualification reports SHA-256。不得覆盖原 `MMFR-A2-v3-pretrain-freeze`。
24. **如果最终 adoption 需要修改正式 config 中的 DataLoader workers，必须在 execution-plan/protocol 中明确登记，但不要称为科学协议 v4。** 前提是第 5 条已经证明 worker 数变化不改变 frozen training input trajectory。如果做不到 exact parity，则正式 workers 保持 8。
25. **本轮结束时只给我六组结果，不要堆日志：** 第一，CPU contention matrix，至少包含 DL workers / OpenCV threads / corruption workers / helper P50/P95；第二，最终采用的 production candidate 及为什么选它；第三，完整 golden parity 与 3-repeat deterministic 结果；第四，old-vs-optimized GPU training trajectory equivalence；第五，优化后 4090 audit-compatible 与 production-like 两套 img/s、GPU utilization、helper/compute 时间；第六，重新计算的 corruption 500e 预计小时数和费用，并回答“基于优化后的 4090，是否还有必要测试 5090”。
26. **最终必须明确列出 Opt-A 与 Opt-B 各自贡献。** 至少形成这样的时间链：  
`original production helper ≈ 1.204 s/batch → Opt-A production helper ≈ 0.613 s/batch → Opt-B production helper = X`；  
以及 production-like GPU throughput：  
`original ≈ 5.97 img/s → optimized = Y img/s`。  
旧 audit probe 的 `4.94 img/s` 单独保留，不能和 production-like 5.97 混成一个 baseline。
27. **停止条件。** 出现任一情况立即停止并汇报，不准自行修科学语义：golden mismatch；RNG stream 变化；sample/batch order 变化；DataLoader worker 改变训练输入；`R_syn/R_sup` 变化；validity 变化；AMP/optimizer trajectory 不等价；需要改 corruption 数学；需要改 batch size/LR/loss；需要 CUDA 重写 corruption；需要使用 ProcessPool 才能继续；需要 CPU/GPU asynchronous lookahead 才能获得进一步收益。
28. **本轮完成后的唯一允许状态：**  
`pipeline-optimization-gpu-equivalence-and-4090-probe-completed-awaiting-senior-review`

并明确写：  
`500e = paused / not authorized`

`5090 probe = not authorized`

这里我对你们当前工作的判断还有一点变化：

**Opt-A 已经把最明显的低效基本解决了，现在 Opt-B 不应该被当成“必须继续大幅优化”。**

因为 clean-instrument 条件下 helper 已经从 **0.816 s 降到约 0.330 s**，而你测到 GPU compute 约 **0.365 s/batch**。如果最终真实 production 环境中 helper 也能接近 0.3–0.4 秒，那么 CPU 生成和 GPU 计算已经接近同一量级。

这时正确动作不是继续花几个小时追求 `0.33→0.20`，而是**马上跑真实 GPU probe**，看整个 step 到底能到什么速度。

所以给下级模型再强调一句：

> **Opt-B 的目标是消除明显的 CPU contention，不是无限优化 CPU；一旦 helper 已接近 GPU compute 时间，就停止微优化，进入 GPU 等价与真实吞吐验证。**

这样最符合你现在保持有卡模式、希望尽快决定是否值得正式跑 500 epoch 的目标。
