## 0. 一句话摘要

v3 的云端 batch size `10` 容量/吞吐 probe 已在单张 RTX 4090 上对**两个身份**各完成一次（各 60 个有效更新步、68 次尝试、8 次 GradScaler 跳过、loss 全有限），checkpoint save→进程销毁→strict reload→继续 step 工程门禁也已完成并通过（续跑轨迹与不中断轨迹在模型、优化器、GradScaler、RNG 四个状态哈希上逐位一致）。probe 同时暴露两条新的实测事实：**corruption 身份比 clean 身份慢 3.4 倍（4.94 vs 16.43 张/秒），使"省钱策略"的第一段反而是贵的一段**；以及 **validation 之后 batch size 10 只剩 1.73 GiB 自由显存（低于历史 2 GiB 余量，但不是 OOM）**。当前没有正式 checkpoint、没有 MMFR mIoU、没有 official-test 结果，两个 500 epoch 训练仍未授权。

## 1. 审计者应先确认的六件事

1. **probe 是"跑过了"，不是"效果通过了"。** 它只回答显存、AMP 有限性、吞吐和单位成本，不产生任何 mIoU 或鲁棒性结论。
2. **两个身份都实际跑了**，不是只测 corruption 一侧；两侧使用同一 seed `772961337`、同一 batch size `10`、同一 `train-dev`、同一 pretrained。
3. **checkpoint 门禁的判定是"续跑 == 不中断"**，依据是四个状态 component 哈希逐位相同、`mismatches=[]`，而不是"能读出来"。
4. **显存安全闸被触发过两次，而且是本项目自己设的门槛。** 两次都不是 OOM；放宽门槛的决定、原门槛数值和两次数值都完整保留在证据中，没有被删除或改写。
5. **有一个运行在脏工作区上完成，已降级为归档证据**（`attempts/checkpoint-gate-parent-dirty-worktree`），最终验收使用的 parent 运行在干净提交 `cdd9ba09` 上重做。
6. **执行计划已被用户修订为"两阶段省钱策略"**，新增阶段 `MMFR-A2-v3-exploratory-one-arm-screening`，位于 probe 之后、正式 paired 训练之前；它只做成本筛选，不改变主 success gate，也不能把 Quick-B0 当作配对 clean control。

## 6. checkpoint save → 进程销毁 → strict reload → 继续 step 门禁

### 6.1 三条轨迹设计

用的是 corruption 身份（它是省钱策略里先跑的一支），`phase=qualification`、`run_kind=qualification`、`epochs=3`、batch size `10`、`checkpoint_policy` 与 v3 config 一致：

1. **parent**：`--stop-after-completed-epoch 1`，在第 1 个 epoch 边界受控停止，写出 `latest.pth`、`selector-epoch-1.pth`、`best-val-miou.pth` 与 `checkpoint-candidates.json`。
2. **child**：全新进程，`--resume <parent latest.pth>` + `--resume-parent-run-id` + `--resume-checkpoint-sha256`（先校验 SHA-256 再加载），续跑到第 2 个 epoch。
3. **reference**：不中断地连续跑完 2 个 epoch，作为等价性参照。

三者的 `run_id` 天然不同；比较时只允许忽略协议 `run_id` 一项，其余全部进入等价契约。

## 7. 本轮新增的两条实测事实

### 7.1 validation 之后只剩 1.73 GiB 自由显存

- 现象：corruption 身份 batch size `10` 在**完成第 1 个 epoch 的 validation 之后**，第 2 个 epoch 的首个训练步只剩 `1.73 GiB` 自由显存，低于历史 `2 GiB` / `0.10` 余量；**不是 OOM**。
- 复现范围：child（续跑）与 reference（不中断）两条独立轨迹**在同一位置都触发**，因此不是单次偶发。
- 对照：训练期（未经过 validation）corruption 的最小剩余为 `2,330.6 MiB`、clean 为 `3,068.6 MiB`。
- 解释：validation 以 batch `1`、原分辨率 `932×1082` 前向，产生更大的临时张量；PyTorch 缓存分配器在 validation 后保留这些块，导致随后训练步的自由显存下降。
- 影响：正式 500 epoch 每 `10` 个 epoch 会做一次 validation，所以该余量会反复出现；24 GiB 的 4090 在 batch size `10` 下属于"能跑但余量偏紧"，这也是第 10 节待用户决定的事项之一。
- **本门禁的处理方式：** 恢复保真度验证改用**关闭显存安全闸**的方式完成（该门禁只考察存档/重载正确性，不考察容量）。两次因闸中止的运行分别归档为 `attempts/checkpoint-gate-child-attempt1-vram-gate` 与 `attempts/checkpoint-gate-reference-attempt1-vram-gate`。

### 7.2 corruption 训练比 clean 慢约 3.4 倍（成本不对称）

- 实测：`16.43` vs `4.94` 张/秒，同一 GPU、同一 batch size、同一数据、同一 seed。
- 原因方向：v3 corruption 在本进程内、GPU 之前对每个样本做 uint8 往返与 OpenCV 风格的空间变换（noise/blur/quantization/misalignment/spatial_dropout），这部分是 CPU 墙钟；clean 身份不承担该开销。
- 后果：**用户提出的"两阶段省钱策略"里，第一段（corruption）反而比第二段（clean）贵**。策略本身仍然成立（只有 corruption 那一支才能回答"有没有苗头"），但预算方向与直觉相反，必须显式记录。

## 8. 基于实测的成本与时间预算

- 步数模型：`iterations_per_epoch = 1277 // 10 + 1 = 128`；`500 epoch = 64,000` 个优化器步。
- 纯训练时间外推（按实测每步墙钟，已包含 probe 的 telemetry 哈希开销，未含 validation）：corruption 约 `129,536` 秒 ≈ `36.0` 小时；clean 约 `38,976` 秒 ≈ `10.8` 小时。
- 换算费用（`1.88 元/小时`，不含云盘与镜像）：corruption ≈ `67` 元；clean ≈ `20` 元。
- 对照：Quick-B0 的 500 epoch 实际训练为 `13 小时 37 分 40 秒`（含 validation 与早期环境开销），与 clean 侧的 `10.8` 小时纯训练量级一致。
- 因此 one-arm screening（先跑 corruption）应预算约 `36–40` 小时、`68–75` 元；若后续再跑 clean control，再加约 `11–14` 小时、`21–27` 元。
- 该预算没有乘任何加速因子，也没有把 `torch.compile` 打开（v3 首轮冻结为关闭）。
