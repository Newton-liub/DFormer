# DFormer 阶段报告格式

Markdown 是正式事实正文。根据实际内容选用章节，不输出空章节，也不为了套模板重复信息。

## 推荐结构

```markdown
# <项目或主题>阶段工作汇报

- 汇报周期：<起点> 至 <终点>
- 报告对象：<组会/研发/交接等>
- 证据边界：<提交区间、任务范围或其他检查点>
- 当前状态：<一句话概括>

## 一、本阶段工作概述

<目标、主要完成事项和整体结论。>

## 二、主要工作进展

### 2.1 <工作项>

- 状态：<已完成并验证/已完成但尚未验证/正在进行/仅提出或计划实施>
- 问题：<为什么要处理>
- 措施：<实际完成的工作>
- 原理与取舍：<必要时说明>
- 结果与证据：<结果、路径、指标或验证>
- 后续：<尚需完成的事项>

## 三、代码与配置改动

<仅在存在相关改动时输出。说明文件或符号、行为变化和作用。>

## 四、实验与验证结果

<仅在存在运行或实验时输出。说明配置、数据、checkpoint、指标、环境和验证状态。>

## 五、数据处理或文献分析

<只输出本阶段实际涉及的部分，区分外部结论和本地验证。>

## 六、当前问题与风险

<未解决问题、证据缺口、风险、阻塞原因和影响。>

## 七、下一步计划

1. <具体、可执行、可判断完成的任务>
2. <下一项任务>

## 八、复现或交接说明

<仅在需要复现、迁移或交接时输出。>
```

## 写作要求

- 概述优先写结果，不按聊天时间流水记账；
- 一个主要工作项只使用一种状态；
- “完成”必须对应已落地事实，“验证”必须对应可描述的检查；
- 关键指标保留名称、数值、单位、数据范围和来源；
- 失败实验可以写入，但要说明失败条件、已排除因素和下一步；
- 下一步使用动词开头，避免“继续研究”“进一步优化”等不可验证表述；
- 代码路径、命令和配置使用行内代码；
- 需要补充的信息统一标记为 `<待补充>`。

## Canvas 转换契约

Canvas 从 Markdown 正文中选择信息，不重新调查或产生新结论。建议映射：

- 标题区：周期、版本、主题和当前状态；
- 核心结论：本阶段最重要的 1 至 3 项结果；
- 进展区：按四类状态组织主要工作；
- 指标区：只展示来源完整、单位明确的真实数据；
- 风险区：未验证事项、阻塞和证据缺口；
- 下一步：具体任务及其依赖关系；
- 页脚：Markdown 报告路径、证据范围和生成日期。

不适合展示的路径细节、长命令和完整复现步骤保留在 Markdown 中。Canvas 文件名与页面内必须显示同一语义版本号。
