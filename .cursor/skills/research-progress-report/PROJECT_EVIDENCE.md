# DFormer 汇报证据映射

仅在本次汇报涉及对应工作时读取相关材料。路径不存在或内容不足时，不做推断。

## 证据优先级

同一事实存在冲突时，默认按以下顺序判断，并在报告中保留必要限定：

1. 当前任务的直接运行结果、实验日志和评估输出；
2. Git diff、提交记录和实际代码或配置；
3. 数据处理产物、统计结果和可复现命令；
4. 项目文档与当前对话中有明确依据的说明；
5. 论文、官方实现和外部资料；
6. 仅讨论但未执行的方案。

低优先级材料不能覆盖高优先级事实。README 中的官方性能只代表上游项目，不等于本地复现实验结果。

## 代码与配置

优先检查：

- `models/encoders/`：DFormer、DFormerv2 编码器；
- `models/decoders/`：分割解码器；
- `models/losses/`：损失函数；
- `utils/dataloader/`：RGB-X 数据读取和组织；
- `utils/train.py`、`utils/eval.py`、`utils/infer.py`：训练、评估和推理流程；
- `local_configs/`：数据集、模型、训练与评估配置；
- `mmseg/`：上游或兼容实现，只有本阶段实际改动时才展开。

代码汇报至少说明相关文件或符号、改动前后行为和验证方式。不要仅根据文件修改时间推断工作内容。

## 实验与运行结果

可能的证据包括：

- 当前会话中的训练、评估和测试命令输出；
- checkpoint 对应的配置与日志；
- 指标文件、TensorBoard 数据或人工记录；
- GPU 云端任务状态和持久化日志；
- 同一环境和设备上的延迟、显存、参数量或 FLOPs 结果。

实验条目尽量包含：

- 数据集和划分；
- 模型与配置路径；
- checkpoint 或运行标识；
- 关键超参数；
- 指标名称和数值；
- 运行环境与设备；
- 是否完成、是否可复现、是否经过复核。

缺少日志、配置或 checkpoint 关联关系时，将结论标记为尚未充分验证。

## 数据处理

优先检查：

- `doc/dataset.md`；
- `doc/museg-dformer-data-processing-review.md`；
- `doc/openlist-cloud-download-guide.md`；
- 实际执行的数据脚本、目录结构、清单和统计输出；
- 数据集论文及其官方说明。

区分“原始数据集事实”“本地处理规则”“处理完成情况”和“模型可用性验证”。文件存在不等于数据正确，格式检查通过也不等于训练流程已验证。

## 文献与方案

本项目 `paper/` 中包含 DFormerv2 和 1-MUSeg/MUSeg 相关论文。只有当文献确实参与本阶段决策、实现或对照时才写入报告。

论文结论与本地验证必须分开表述：

- “论文报告……”表示外部结论；
- “本项目复现/观察到……”必须有本地证据；
- 方案讨论没有实现证据时归入“仅提出或计划实施”。

## Git 与对话

Git 用于确认改动边界、文件差异和提交基线，不单独证明功能正确。工作区未提交改动可能来自用户或其他任务，写入报告前必须确认属于本次范围。

对话记录用于解释目标、决策和过程，但不能替代代码、日志或运行结果。跨会话边界优先使用 `doc/reports/report-index.json` 中的正式检查点。

## 证据引用方式

报告正文保持可读，不必给每句话附路径；但关键结论应能通过以下信息回溯：

- 文件路径与符号名；
- 配置路径和关键参数；
- 执行命令；
- 日志或结果路径；
- Git 提交或差异范围；
- 论文标题、版本或来源。

无法确认的信息写 `<待补充>`，不要构造占位数值。
