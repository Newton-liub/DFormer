# MUSeg 研究计划创建

## 适用范围

当用户要求新建、重组或扩展 MUSeg 研究/实验计划时使用本 Skill。计划文件统一放在 `doc/plans/` 下；它们描述研究设计和形成时点，不自动授予代码修改、GPU、训练、长耗时评估、云资源或 official test（官方测试集）权限。

本 Skill 面向 MUSeg 计划，不替代项目实时状态规则。若任务同时要求执行代码或实验，先完成计划边界，再按项目授权和验证预算单独处理。

## 一、开始前必须确认的事实

1. 先读取 `doc/main/MUSeg-current-status.md`。它是项目范围内当前事实、授权边界、证据入口和恢复规则的唯一实时入口。
2. 只要涉及研究选择、阈值、数据职责、结论边界或开放问题，再读取 `doc/main/MUSeg-open-decisions.md`。
3. 读取用户指定的既有计划作为结构参考；默认定点读取其总规划、最小上下文和一个代表性子计划，不全仓通读历史材料。
4. 读取 `doc/plans/README.md` 和 `doc/guides/README.md`，遵守目录索引和文档状态头规范。
5. 从实时状态确认当前是否有已授权执行计划。计划中的“当前任务”“下一步”和“恢复点”只能描述计划形成时点，不得覆盖实时状态。

计划创建属于纯文本工作：默认只做内容、链接和差异检查，不运行项目测试、GPU、训练、云任务或 official test。

## 二、目录与文件布局

默认新计划目录为：

```text
doc/plans/<YYYY-MM>-<topic>/
├── 00-总方向规划.md
├── 01-新对话最小上下文与当前任务.md
├── 02-<第一个子计划>.md
├── 03-<后续子计划方向>.md
└── 参考资料/                         # 需要时创建
```

- 用户明确要求延期或归档时，使用项目已有的 `deferred/` 或 `archive/` 目录，并在状态头中写清“延期/未执行”或“已封存”。不要因为文件夹名字存在就把新计划错误放入历史目录。
- `doc/plans/` 不存在时先创建；目标计划目录和所需子目录不存在时创建。已有文件不得覆盖，先读取并选择新文件名或向用户说明冲突。
- 子计划数量按流程长度决定。复杂或有条件分支时使用独立文件；流程短且顺序固定时，可以把所有子计划写在一个文件中，但仍须在总规划和最小上下文中标明任务顺序。
- 需要补充提示词、文献编号或长参考材料时放入 `参考资料/` 或 `补充内容/`，不能让它们承担实时状态职责。

## 三、三个必备层次及职责

### 1. `00-总方向规划.md`：回答“为什么做、怎样收口”

必须包含：

- 文档角色、计划状态、形成/核验日期、实时入口和后继关系；
- 一句话目标：研究问题、对象、预期贡献和不主张的结论；
- 关键概念与判断边界：首次出现的缩写给出全称、职责和大白话解释；
- 固定身份和不可变边界：模型、checkpoint（模型参数快照）、数据 split、输入契约、evaluator（评估器）、metric geometry（指标计分网格）、代码/protocol 身份、official test 状态；
- 与 `MUSeg-current-status.md` 的关系：实时状态优先，计划只记录计划形成时点的设计状态；
- 子计划清单及链接，注明每个子计划的前置条件、交付物、是否需要用户授权和后继关系；
- 任务顺序、门禁、条件分支、失败/不确定/协议阻塞的合法终点；
- 证据要求：命令、环境、退出码、产物哈希、失败/恢复历史、official-test 拒绝状态；
- 结论分层：工程检查、MVE（最小可行实验）、development（开发证据）、正式统计结果和现实部署推断不能混写；
- 明确禁止事项：未授权的代码/实验/云操作、读取 official test、结果后改阈值或追加条件，以及把历史证据当作新证据。

总规划描述完整方向，但不要把尚未执行的设计写成已完成事实，也不要把所有后续子计划伪装成已经详细冻结的步骤。

### 2. `01-新对话最小上下文与当前任务.md`：回答“新对话先读什么、从哪里开始”

必须包含：

- 文档角色和计划状态；
- 按顺序排列的前 3 个必读入口：实时状态、本文件、总方向规划；涉及实验口径时再读开放决策；
- **计划内当前状态**：只记录本计划相关的阶段、当前计划、已完成/未完成子计划、准确恢复点、阻塞项和相关引用链接；不能复制或替代项目全局实时状态；
- 当前执行子计划的唯一链接、前序计划/报告/证据链接和后继候选链接；没有执行计划时明确写“未授权/不在恢复点”；
- 最少需要知道的固定身份、数据职责、official-test 边界和本次不允许做的操作；
- 本次新对话的原拟议任务卡：只写一个最小交付物，说明输入、输出、前置门禁和停止条件；
- 按需读取的文件和搜索范围；默认禁止全仓搜索、大型日志/预测/checkpoint/数据读取；
- 状态更新与验证预算：纯文档只做差异检查，代码/实验需按风险定点验证，完整测试和高成本操作另行授权；
- 可直接粘贴给新对话的短提示词。

这里的“计划内当前状态”不等于 `MUSeg-current-status.md`：前者只回答“这个计划走到哪一步以及链接哪份当前执行计划”，后者回答“整个项目现在有哪些事实、授权和恢复规则”。若两者冲突，始终以实时状态为准。

### 3. 子计划：回答“这个阶段具体怎样做”

第一个子计划必须详细规划；后续子计划默认只保留方向、触发条件、主要交付物和禁止越界的边界，等上一个子计划完成并形成证据后再详细规划下一个。不要为追求文件数量预先编写一整套可能被实验结果改变的细节。

每个子计划至少写明：

- 文档角色、计划状态、形成/核验日期、实时入口、上级总规划和前后继关系；
- 本子计划的目标、问题/假设、输入身份和不变量；
- 前置条件、用户授权条件、最小交付物和完成判据；
- 执行步骤的边界：只改变哪些变量，哪些变量保持不变；
- 数据、代码、结果、证据和产物存放位置；大型数据、预测、checkpoint、日志和凭据不进 Git；
- `protocol-blocked`、`stop`、`inconclusive` 等合法终点及准确恢复方式；
- 失败时保留现场，不覆盖原始证据；影响数值语义时重新建立 protocol identity；
- 验证预算和状态更新要求；实际执行后才能写“已完成/通过”。

后续子计划可以先使用如下短模板：

```markdown
## 后续方向（待前一子计划完成后细化）

- **触发条件：** `<前一子计划的明确结果> + 用户批准`。
- **方向：** `<问题、方法或实验对象>`。
- **主要交付物：** `<代码/协议/实验/裁决>`。
- **不提前冻结：** `<会受前一结果影响的参数、条件、阈值>`。
- **禁止越界：** 不提前运行 GPU、训练、云任务或 official test；不把本方向写成已授权。
- **细化时机：** 前一子计划的证据、状态和恢复点写入后，再创建或补充本子计划的详细步骤。
```

## 四、子计划递进规则

默认按照以下漏斗顺序设计，不得无理由倒置：

1. 先冻结研究对象、数据职责、checkpoint、输入契约、evaluator、protocol 和结论边界。
2. 先做最小身份/完整性/CPU 检查，再做正式数据评价。
3. 先验证问题是否存在，再验证最低复杂度方案是否有效。
4. 先低自由度、单核心变量、paired（配对）和同源输出，再进入高自由度方法、迁移检查或训练。
5. 每个条件分支写出明确解锁条件，例如 `DVC-pass + 用户明确批准`，并写出 `stop`、`inconclusive` 和 `protocol-blocked` 的处理。
6. 前一阶段没有形成可核验证据时，不详细设计或执行下一阶段；不得用计划预计结果代替事实。
7. 只要模型、数据、evaluator、统计口径、预算或授权范围改变，就新建 protocol identity 或新计划，不在原文件静默扩展。
8. 任何官方测试集读取、解封或 allowlist 变更都必须独立门禁和独立授权；计划默认保持 `sealed_unread`。

短流程可合并子计划，但不能删除身份冻结、授权边界、停止条件、证据规则和状态更新规则。

## 五、MVE 实验命名规则

可以使用 `-A1`、`-B1` 这种紧凑后缀，但它们只能作为**完整语义名称的一部分**，不能单独作为实验身份。推荐把它解释为“分支字母 + 该分支内的阶段号”：看到名称即可知道属于 A 还是 B，也能知道该分支走到第几阶段；前面的语义词根负责避免跨计划和历史名称混淆。

### 推荐格式

```text
<语义实验简称>-<分支><阶段>-<条件或用途>-v<protocol版本>
```

例如：

- `DVC-A1-valdev-v1`：Depth-validity corruption check，A 分支第 1 阶段，验证人工深度退化问题；
- `DVG-B1-zero-train-v1`：Depth-validity gating，B 分支第 1 阶段，验证门控方案的零训练行为；
- `GTC-B1-clean-CE-v1`：Global-temperature clean calibration，B 分支第 1 阶段，在独立 calibration/evaluation 数据职责上验证全局温度校准；
- `DVC-A2-natural-strata-v1`：同一 DVC 方向 A 分支第 2 阶段，检查自然无效深度分层。

### 具体规则

- 首次出现时先写完整名称、职责和本计划的 A/B 图例。例如默认可定义：`A = 问题/现象验证`，`B = 方案/干预验证`；如果某个计划采用不同含义，必须在 `00-总方向规划.md` 中声明该计划自己的图例。
- `A1`、`A2`、`B1`、`B2` 的数字只表示**当前实验族内部**的阶段顺序，不表示全项目统一阶段，也不自动继承历史计划含义。
- 不使用裸名称 `A1`、`A2`、`B1`、`B2`、`MVE` 或 `A/B` 作为文件名、manifest ID、结果状态或报告标题。至少保留语义前缀，例如 `DVC-A1`、`DVG-B1`、`GTC-B1`。
- 语义前缀应包含研究对象和用途；`DVC` 表示 Depth-validity corruption check，`DVG` 表示 Depth-validity gating，`GTC` 表示 Global-temperature clean calibration。必要时在计划开头建立“名称—职责—历史别名”映射。
- 条件、数据职责和 protocol 版本放在后缀中，例如 `valdev`、`clean-CE`、`corruption`、`v1`；不要把阶段号当作 protocol 版本。
- 如果必须引用历史名称，使用“历史 A2（本计划对应 `DVC-A1`）”的写法，并说明历史名称不构成当前实验身份。
- 项目已有 `B1 safe_masked_mean` 数值稳定性修复。新实验可以使用 `DVG-B1` 这样的完整名称，但不得把它简称为裸 `B1`，以免与该修复混淆。
- 在总规划、最小上下文、子计划、manifest、结果状态和报告中统一使用同一完整名称；名称一旦进入 protocol identity，不因实验结果改变。

## 六、引用与状态头模板

每个新建或实质更新的计划文档标题后，按 `doc/guides/README.md` 写状态头，至少包括：

```markdown
> **文档角色：** 总方向规划 / 新对话最小上下文 / 条件式子计划 / 历史执行计划。
> **计划状态：** 待规划 / 当前执行 / 暂停 / 延期未执行 / 已完成 / 已封存。
> **形成或核验时点：** YYYY-MM-DD 或 YYYY-MM-DD HH:MM UTC。
> **实时入口：** [`MUSeg-current-status.md`](相对路径)。
> **研究选择：** 涉及研究口径时链接 [`MUSeg-open-decisions.md`](相对路径)。
> **上级方向：** [`00-总方向规划.md`](相对路径)。
> **当前/后继关系：** 当前执行子计划或后继候选的链接；没有则明确写无。
```

只有 `doc/main/MUSeg-current-status.md` 可以声明自己是实时状态入口。计划文档必须使用“计划内当前状态”或“形成时点状态”，不得自称项目当前事实源。

## 七、创建后检查

完成计划后只做以下最小检查：

- 检查 `SKILL.md` 或计划 Markdown 的 frontmatter/标题/状态头完整；
- 检查相对链接目标存在，或明确标记为待创建/待确认；
- 检查总计划、最小上下文和子计划没有互相维护冲突的 checkpoint、split、evaluator 或授权事实；
- 检查首次出现的缩写有全称、职责和必要的大白话解释；
- 检查后续子计划没有提前写死会依赖实验结果的细节；
- 检查所有 MVE 名称不只使用 `A1/A2/B1/B2`，并能区分方向、条件和 protocol；
- 检查差异，不运行项目测试或高成本验证；
- 如新增计划根目录需要被导航，更新 `doc/plans/README.md` 的链接，但不要把计划预计状态写成实时完成事实。

最终答复只报告实际完成的文档创建和内容/链接/差异检查；没有运行的项目测试、GPU、训练、云任务或 official test 明确写为未运行。
