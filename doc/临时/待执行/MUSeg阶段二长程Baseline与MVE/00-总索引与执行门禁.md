# MUSeg 阶段二：DFormerv2-S 长程 baseline 与后续 MVE 总索引

> 文档状态：待执行；本目录只保存计划，不代表已经实现或运行。
>
> 起点定义：这里的“阶段二”是“建立 DFormerv2-S 长程 baseline”，不是旧交接文档中的 GPU preflight 阶段。
>
> 执行模型：默认由 Terra 按文件顺序执行；标为 **Sol 必须执行/复核** 的任务不得由 Terra 独立决策。

## 1. 本阶段目标

1. 将历史 20-epoch 链路降级为 qualification（工程资格验证），不再称为正式 baseline。
2. 从 MUSeg 官方 `train.txt=1595` 内按 location group 构建固定 development train/validation；官方 `test.txt=1576` 在开发阶段封存。
3. 建立可恢复、可审计、三随机种子、最长 500 epochs 的 DFormerv2-S 长程训练链路。
4. 仅用 validation 冻结训练周期、checkpoint 选择和正式实验协议。
5. 在成熟 baseline 上重新运行正式 A2；历史 epoch-10/16 图 A2 仅作为 pilot 证据。
6. 只有正式 A2 达到预注册门槛才进入 B2；否则停止 B2 主线。

## 2. 明确不做的事情

- 不在本轮计划编写阶段连接云端、安装依赖、运行 GPU、生成数据划分或修改训练代码。
- 不把官方 test 用于选择 epoch、超参数、seed、A2 条件或 B2 结构。
- 不把单次 20 epochs、单个最好 seed 或 test 最优 checkpoint 写成正式 baseline。
- 不重新研究或撤销已经完成的 A1/B1 张量级结论；只补真实模型混合 batch 回归。
- 不默认复现论文中的 DFormer-S 数值。论文协议已经在阶段一核对；本阶段目标模型是 DFormerv2-S。若用户另行要求严格 DFormer-S 数值复现，必须另立计划。

## 3. 全局事实与固定边界

- MUSeg 论文：官方 train/test 为 1595/1576；同一拍摄位置组不得跨 split；所有模型 500 epochs、3 seeds。
- 本地静态核验：官方 train 有 958 个位置组，test 有 957 个位置组，位置组交集为 0。
- 位置组键来自文件名的前四段，例如 `06-01-01-0215-...` 的键是 `06-01-01-0215`。
- 当前代码 `local_configs/MUSeg/DFormerv2_S_4090.py` 将训练期 `eval_source` 指向官方 `test.txt`，必须在长程训练前纠正。
- 当前 `utils/train.py` 只在 epoch 1、每 10 epochs 和 `checkpoint_start_epoch` 之后验证；best、resume、seed 和元数据能力不足，必须先改造。
- 当前 A2 工具只覆盖 16 图、block mask、`q=0/0.3/0.5`、单 seed；B2 尚未实现。
- 当前工作区可能包含计划外的 Cursor agent/workflow 修改。执行者不得覆盖、清理、暂存或提交不属于当前子计划的文件。

## 5. 全局人工门禁

- **门禁 A：划分冻结。** 用户确认 train-dev/val-dev 数量、位置组零重叠、六矿分布、类别分布和 SHA-256。
- **门禁 B：代码链路冻结。** 01–03 经过测试和 Sol 复核后才能申请 GPU qualification。
- **门禁 C：batch 选择。** 4090 探测后先报告，用户确认正式 batch。
- **门禁 D：开发长训。** qualification 和 resume 演练通过后，用户批准长程 dev 训练。
- **门禁 E：正式协议冻结。** Sol 只根据 validation 曲线提出训练周期和选择规则，用户确认后不再修改。
- **门禁 F：test 解封。** 三个正式 seed 的预定 checkpoint、哈希、退出码全部合格后，用户明确批准 test 评估。
- **门禁 G：B2。** 正式 A2 达到门槛且 Sol 签署 A2-G 后才允许进入 09。

## 6. 每个执行代理的统一规则

1. 开始前读本索引、当前子计划、所有前置完成报告和实际目标文件。
2. 先运行 `git status --short`；发现计划外改动时停止，不得 stash/reset/覆盖。
3. 一个子计划只产生一个边界清晰的代码提交；运行日志、数据、权重、checkpoint、凭据不进 Git。
4. 代码修改前先补或设计失败测试；修改后只运行受影响测试，再运行计划指定的完整测试。
5. 不顺手重构，不更换框架，不创建新 Conda/venv，不改原始数据。
6. API key 只从环境读取，不回显、不写文件。
7. 需要修改计划外文件、改变实验协议或解释异常时停止并升级给 Sol。
8. 执行报告必须包含 commit、命令、退出码、测试结果、产物路径与哈希、未解决风险和 `git status --short`。

## 7. Git 与证据规则

- 计划文件和小型代码/测试可提交；生成的数据 split 是否提交由 01 的协议决定，但必须能由 manifest 和固定算法重建。
- 每个代码阶段单独提交，提交消息说明阶段编号；不得把多个阶段压成一个不可审计提交。
- 正式运行必须使用干净 commit；运行中若修代码，当前 run 作废，修复独立提交后从受影响阶段重来。
- 输出根目录按实验 ID/seed 隔离；禁止多个 run 共用 checkpoint 或预测目录。
- 所有 JSON/CSV 汇总应包含 schema version、完整 Git commit、split SHA-256、checkpoint SHA-256、seed 和生成命令。
