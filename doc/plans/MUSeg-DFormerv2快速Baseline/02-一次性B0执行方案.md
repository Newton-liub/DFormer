# MUSeg DFormerv2-S：一次性 B0 执行方案

> **文档角色：** 当前 B0 的执行方案；目标是只训练一次 single-seed development B0，并形成后续模块消融可复用的内部基线。
> **上级方向：** [`00-总方向规划.md`](./00-总方向规划.md)
> **实时状态：** [`MUSeg-current-status.md`](../../main/MUSeg-current-status.md)
> **研究选择：** [`MUSeg-open-decisions.md`](../../main/MUSeg-open-decisions.md)
> **状态：** 训练参数、FP32 主 evaluator、top 3 + latest、protocol v3 和本地评估位置均已冻结；任务 1“本地实现与定点检查”和任务 2“无卡自动关机门禁”已完成。下一步是仍需单独授权的一次 RTX 4090 B0 训练。
> **执行组织：** 通常按依赖和上下文边界使用 1–3 个任务；本方案因增加独立的无卡自动关机门禁，共使用 4 个可续接任务，不再继续拆分。

## 1. 目标与交付

本方案只完成一个可靠、可复用的 B0：

1. 按官方预训练输入语义使用 RGB；
2. 补齐 B0 必需的 config、protocol 和主 evaluator；
3. 做不产生研究结论的最小技术检查；
4. 通过一次无卡自动关机门禁；
5. 从官方预训练权重开始训练一次 500-epoch B0；
6. 用主 evaluator 从预登记候选 checkpoint 中选出最终 B0；
7. 固化 checkpoint、指标、配置、代码、数据划分和 evaluator 身份，供后续模块做同口径消融。

本轮不训练第二或第三个 B0 seed，不解封 official test（官方测试集），也不在 B0 任务中加入模块实现。

## 2. 任务组织与上下文续接

执行使用 4 个有真实边界的任务包：

1. **本地实现与定点检查（已完成）**：已完成 config、protocol、evaluator、66 项聚焦 CPU 检查和获批的本地最大样本/计时检查；主 evaluator 运行位置冻结为本地。
2. **无卡自动关机门禁（已完成）**：实例 `cpod-1tyvjsiu6ahe` 已在无卡模式完成模拟 workload、报告生成、证据同步、哈希复核、控制面停止和 `Stopped` 状态确认；没有产生 B0 指标。
3. **一次 B0 训练**：无卡门禁通过且用户另行授权后，启动 RTX 4090 训练，完成 500 epoch 和候选 checkpoint 清单；不中途扩展实验。
4. **主评估与证据收口**：按已选运行位置评估候选 checkpoint，确定最终 B0，核验哈希并更新实时状态。

这 4 个任务按顺序执行，可以分属不同对话。自动关机门禁涉及独立云资源生命周期和计费风险，因此不与代码实现或正式训练混在同一任务；除此之外不继续拆分。每个任务结束时必须把已完成内容、未完成内容、冻结身份和下一条准确命令写入 [`MUSeg-current-status.md`](../../main/MUSeg-current-status.md)，防止上下文压缩或换对话后丢失信息。

## 3. 输入与训练协议

### 3.1 固定身份

- 模型：DFormerv2-S，HAM decoder，保留 B1 `safe_masked_mean`。
- 预训练：官方 `DFormerv2_Small_pretrained.pth`，110,203,103 bytes，SHA-256 `19116988fc86dc9f3e879282237941e11b9b1b5c480edb51e92807311dbc11a6`。
- `train-dev`：1,277 条，SHA-256 `a6b15b63f6d5193e3928ea24ada25be403a48e68d1c1f9372cdbbc3fe5cd8470`。
- `val-dev`：318 条，SHA-256 `1d0719d8f64f016d48995c25ab66d4004d76b7155d9efeef7cbb7454c0dd0e83`。
- official test：保持 `sealed_unread`。

### 3.2 输入与增强

- 彩色输入：OpenCV 读取后 BGR→RGB；normalization identity 为 `rgb-imagenet-rgb-order-v1`；mean `[0.485, 0.456, 0.406]`，std `[0.229, 0.224, 0.225]`。
- 选择 RGB 的依据是与官方预训练通道语义一致；本方案不把它表述为 RGB/BGR 性能比较结论。
- Depth：继续使用现有全局量化 8-bit 图；单通道复制为 3 通道；每通道 mean `0.48`、std `0.28`；本轮不加入 depth-validity mask/gating。
- 训练随机尺度：`[0.5, 0.75, 1.0, 1.25, 1.5, 1.75]`，均匀离散采样。
- 水平镜像概率：`0.5`；crop 为高 480、宽 640。
- RGB/Depth 缩放使用双线性，Label 使用最近邻；不足部分在 normalization 后为 RGB/Depth 补 0，Label 补 255。
- 不增加颜色抖动、旋转、MixUp、CutMix 或其他新增强。

### 3.3 优化与预算

- AdamW，base learning rate `6e-5`，weight decay `0.01`，poly power `0.9`。
- 500 epoch，warmup 10 epoch，AMP 开启，compile 与 SyncBN 关闭。
- 单 RTX 4090，batch 10，seed `772961337`，`run_kind=standard`。
- batch 10 已用于同尺寸训练链；随机尺度后仍裁剪到 480×640，颜色转换不增加张量尺寸，因此不安排独立长训练 probe。
- 理论每 epoch 128 次 loop attempt，总计 64,000 attempts；实际 completed optimizer updates 与 AMP skipped steps 分别记录。

历史同规模运行到 epoch 460 才出现最佳在线结果，因此在只训练一次的前提下保留 500 epoch，不主动缩短训练预算。

## 4. 主 evaluator 契约

主模式命名为 `msflip-whole-original-grid-v1`：

- 尺度 `[0.5, 0.75, 1.0, 1.25, 1.5]`，每尺度原图和水平翻转，共 10 个推理 view；
- 缩放基准是原始 RGB/Depth 高宽，二者同步使用 OpenCV 双线性缩放；
- normalization 后只在右侧和底部补 0 到 32 的倍数；
- 每个 view 的 logits 先 unflip、去 padding，再用 PyTorch bilinear、`align_corners=False` 恢复到原始 Label 网格；
- 10 个 view 均使用 FP32 输入、FP32 模型前向和 FP32 输出；TF32 关闭，pre-softmax logits 以 FP32 算术平均后再取 argmax；
- 默认 batch size 为 1，并使用 `torch.inference_mode()`；主模式前向硬冻结为 FP32，AMP 请求会被拒绝，不因显存或速度自动改变；
- 输出 mIoU、mAcc、mF1、per-class、confusion matrix、样本数、每个 view 的输入/恢复尺寸、峰值显存、运行环境和全部哈希身份。

只用 `val-dev` 最大尺寸样本做一次尺度 1.5 的前向可行性检查。它不选择模型、不产生实验指标。若整图 OOM，停止并由用户决定是否显式改为 sliding；不自动切换 evaluator 几何。

2026-08-30 已完成该检查：程序先核验 checkpoint SHA-256 `b62ca049e6a647aca109c70e80823cec8e36ae1cc1df27e3bcf2b1d215b160bf` 和 val-dev SHA-256 `1d0719d8f64f016d48995c25ab66d4004d76b7155d9efeef7cbb7454c0dd0e83`，再选择标签像素数最大的样本 `06-01-01-0352-230920140646-10-99`。原图 `932×1082`，尺度 1.5 后 `1398×1623`，padding 后 `1408×1632`；FP32 原图/翻转两个 view 分别为 `2.095559`/`1.079008` 秒，峰值 allocated/reserved 显存为 `4,977,021,952`/`6,511,656,960` bytes，状态 completed。结果显式记录 `metrics_computed=false`，证据见 `cloud/DFormer-stage05-evidence/posteval/quick-b0-scale1.5-max-sample-fp32-technical-check.json`。大白话说，这只证明本机能跑最吃显存的冻结 view，不是模型指标。

## 5. Checkpoint 候选与最终选择

训练期采用低成本 selector（候选筛选器）：

1. 从 epoch 10 开始，每 10 epoch 运行一次 `original-full`、尺度 1.0、无 flip validation；
2. 动态保留单尺度 mIoU 最高的 3 个 checkpoint，并另外保留 `latest.pth`；相同 mIoU 时优先更早 epoch；
3. 500 epoch 结束后生成不可变候选清单，对“单尺度 top 3 + latest”按 checkpoint SHA-256 去重，最多 4 个；
4. 对清单内全部候选运行主 evaluator；
5. 最终 B0 由主 evaluator mIoU 最高者决定；相同主 mIoU 时依次比较主 mAcc、选择更早 epoch；
6. 保留并报告所有候选的单尺度和主指标，不能只留下获胜数字。

五尺度翻转约为单尺度整图 `11.25` 倍输入像素量。单尺度与主 evaluator 通常相关，但不保证 checkpoint 排序完全一致；top 3 加 latest 用于降低误选风险，最终模型仍由主 evaluator 决定。

默认不评估“训练后期所有 checkpoint”。增加候选会线性增加约 3,180 次 view 前向/每 checkpoint（318 个样本 × 10 views），而同时运行多个 evaluator 还可能造成显存竞争。若要扩大到预登记的后期 checkpoint 窗口，必须在训练前写清 epoch 集合、存储量、运行位置和成本上限，不能看到曲线后临时挑范围。

## 6. 主评估运行位置

Checkpoint 可以从云端带回本地运行主 evaluator。结果是否有效取决于冻结身份，不取决于运行机器的位置。

### 6.1 已核验的本机能力与本地验收条件

2026-08-30 已直接核验本机：

- GPU：NVIDIA GeForce RTX 5060 Laptop GPU，8,151 MiB；驱动 `610.88`；
- CPU：AMD Ryzen 9 8945HX，16 核 32 线程；物理内存约 15.2 GiB；
- `D:` 可用空间约 120.5 GiB；
- `df2` 环境：Python `3.10.20`、PyTorch `2.7.0+cu128`、CUDA available、cuDNN `90701`，并已安装 evaluator 所需的 OpenCV、timm、MMCV 和 MMEngine；
- 当前 base Python 在导入 PyTorch 时触发重复 OpenMP runtime 错误，因此正式本地 evaluator 使用 `df2`，不使用 base 环境，也不采用 `KMP_DUPLICATE_LIB_OK` 绕过错误。

本地结果作为最终 B0 结果还必须满足：

- 本机最大样本尺度 1.5 GPU 可行性检查已通过；训练后的正式本地结果仍须使用同一 `val-dev`、冻结 Git commit、config、protocol 和 evaluator；
- 最大样本技术检查已经在本机通过；正式主评估继续绑定 checkpoint SHA-256、split SHA-256、输入契约、FP32、依赖版本和 `official_test_included=false`；
- 云端训练结束后先同步候选 checkpoint、候选清单和必要运行身份，在本地复核哈希，再停止实例。

同一台本地 RTX 5060 Laptop GPU 的历史 `original-full` 结果对 318 个样本用时 `108.342` 秒。按五尺度翻转 `11.25` 倍输入像素量粗算，约为每 checkpoint `20.3` 分钟，4 个候选约 `81.3` 分钟；该估计不包含尺度 1.5 的显存风险、padding 和非线性吞吐。计划预算设为 2–4 小时，用户接受的本地硬上限为 8 小时。

尺度 1.5 最大样本检查已通过。以该最大样本两 view 合计 `3.174567` 秒，按 `11.25/4.5=2.5` 的像素倍率保守外推，单 checkpoint 约 `42.1` 分钟、4 个候选约 `2.8` 小时；模型加载总开销不会使其超出 2–4 小时计划预算，也明显低于 8 小时硬上限。因此，**主 evaluator 运行位置冻结为本地 RTX 5060 Laptop，按候选清单串行运行**。

### 6.2 云端运行的资源原则

本地不可行时，在训练使用的 RTX 4090 云实例上直接排队评估候选。RTX 4090 有更大的显存和更高的理论算力，但 batch 1、多尺度 CPU resize、图片解码、磁盘读取和频繁同步可能使 evaluator 受 CPU/I/O 限制，因此真实速度不按显卡理论算力线性提升；这可以解释过往云端与本地推理时间接近的现象。

云端执行遵循：

- 数据和 checkpoint 放在实例本地 SSD，避免从网络盘逐样本读取；
- 模型每个 checkpoint 只加载一次，使用 `torch.inference_mode()`、pinned memory 和 non-blocking host-to-device copy；
- DataLoader worker、persistent worker 和 prefetch 只作为不改变指标的吞吐参数，在最大样本/小样本计时检查中冻结；
- 前向 AMP、channels-last 或更大 batch 可能改变数值或显存行为，不作为静默加速项；若采用，必须先做定点一致性检查并写入 evaluator identity；
- 按候选清单连续串行运行 evaluator，单 GPU 默认不并发运行多个 checkpoint，避免模型副本和尺度 1.5 view 争抢显存；
- 多 GPU 或多实例并行主要缩短墙钟时间，不保证减少总实例费用，必须先比较单 checkpoint 实测耗时和计费方式；
- 启动前设置最长评估时限和控制面最晚停止兜底；所有终态先同步结果并核验哈希，再停止实例。

因此，当前冻结顺序是：**云端训练完成后先同步并核验最多 4 个候选，再在本地 RTX 5060 Laptop 串行运行主 evaluator；8 小时仍是异常停手硬上限。** 云端只承担后续获批的 lifecycle-test 和正式训练，不因本地 evaluator 已可行而扩大云端工作。

- 只运行受影响的静态诊断和定点 CPU 测试；本轮获批的 GPU 最大样本/计时检查和无卡云生命周期实测均已完成。

GPU 检查通过后，主 evaluator 已冻结在本地；无卡 lifecycle-test 也已通过。下一步需单独报告正式训练的预计时长、费用、checkpoint 同步方式和控制面最晚停止时刻，取得正式训练授权后只启动一次 B0 workload。

## 8. 无卡自动关机门禁

正式 RTX 4090 任务前必须先完成一次独立的无卡生命周期验证。现有 `tools/preflight_train.py --allow-no-gpu` 只会把“CUDA 不可用”从 error 降为 warning，不能自行模拟训练完成、报告生成或控制面停止，因此需要一个明确标记的 lifecycle-test（生命周期测试）包装器。

测试身份与边界：

- 使用 `run_kind=lifecycle-test`、`simulation=true` 和独立输出目录；
- 不加载模型、不生成 mIoU，不得被 B0 adjudicator（结果裁决器）接受为训练结果；
- 模拟 workload 成功结束，并生成测试专用 terminal result、summary、evidence manifest 和 SHA-256；
- 自动停止使用本机 CompShare CLI 的控制面 `instance stop --yes --wait --timeout`，不把实例内 `shutdown -h` 当作唯一成功证据；
- 启动测试前用 `instance schedule set --at` 设置最晚停止兜底，并用 `instance schedule show` 复核。

一次通过链如下：

1. 用户批准无卡实例或无卡模式的具体资源和最长运行时间；
2. 设置并复核控制面最晚停止兜底；
3. 提交 durable lifecycle-test job，模拟成功 workload 并生成报告；
4. 本地控制器等待 job 终态，取回报告和 manifest，逐项复核 schema、simulation identity 与 SHA-256；
5. 本地控制器自动调用控制面停止，并等待实例进入 `Stopped`；
6. 记录 job 完成、证据取回、stop 请求和 `Stopped` 的 UTC 时间及退出码。

通过条件是：模拟 job 退出码为 0；测试报告齐全且哈希匹配；自动 stop 命令成功；实例在预设 timeout 内达到 `Stopped`；全程不需要人工补发普通停止命令。任何一项失败都阻塞 RTX 4090 B0，先保留现场并修复生命周期链。CPU 定点测试还要覆盖 workload 成功/失败都进入“同步证据后停止”的公共 finally 路径，但本轮云端无卡实测只要求一次成功终态。

该门禁会产生云资源状态变化，实际创建、启动、停止或修改 schedule 前仍需用户单独授权；当前文档不构成执行授权。

## 9. 失败与停手规则

- 实现或定点测试失败：修复后只重复对应定点检查，不扩大到完整测试套件。
- 最大样本整图 OOM：不启动训练，先请用户决定是否改为 sliding evaluator。
- B0 运行发生技术故障：保留日志和现场，判断能否从有效 checkpoint 恢复；恢复同一 run 不计为新增研究 seed，但不得把不连续身份隐藏起来。
- 达到 500 epoch、失败或人工中止后，都先同步必要证据并核验哈希，再停止实例；验收结论不控制是否继续计费。
- 不自动增加 epoch、seed、候选 checkpoint 数量或其他实验。

## 10. B0 在后续模块消融中的角色

本次 B0 是后续模块设计的内部比较基线，不以完整重现论文或三 seed 统计为目标。验收重点是训练和评估链可信、指标量级合理、没有明显类别或数值异常，并且后续比较使用同一口径；不要求与论文数字完全相等。

B0 训练一次后可以持续作为对照，但仅在后续模块保持以下训练契约不变时成立：同一 pretrained、`train-dev`/`val-dev`、seed、数据顺序、epoch、优化器、增强、checkpoint 规则和主 evaluator。模块版本必须从同一 pretrained 独立训练，不能从 B0 最终 checkpoint 接着训练后再称为公平消融。

单 seed 足以用于模块探索、淘汰和初步消融，但不能估计随机方差。若某个模块增益很小、接近训练波动或将决定重要结论，应对 B0 和该模块增加同 seed 重复或额外 seed 的成对确认；当前不预先要求三 seed，也不因此阻塞模块设计。

若后续改变训练预算、增强、优化器、数据或 evaluator，现有 B0 不再是严格配对对照；需要保留旧结论边界，或在新协议下重新训练 B0。
